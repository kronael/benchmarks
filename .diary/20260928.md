## 12:05

The load gate was reading the wrong machine. `bench.QUIET_LOAD_15` compared
`/proc/loadavg` against 1.6, and that file is the host's — it counts every CPU
the host has while a measurement runs inside a two-CPU cpuset. Measured during a
run: host load 36.2 over pinned cores that were 17% idle with zero steal, and
later host load 48.9 over cores 26.4% busy. The two numbers do not track.

`bench.contention()` now samples the busy fraction of the pinned cores before
the run and every result carries it. It does not decide the status yet, because
that changes the method statement. `BUGS.md` carries the proposal.

## 12:20

`make bench` compiled as root and that was nearly invisible. Every measurement
Makefile had `bench: build`, and the documented command is
`sudo chrt -f 80 taskset -c 0,1 make bench`, so the build recipe re-entered as
root. Under `sudo` HOME is root's, `GOTOOLCHAIN=go1.27.1` cannot resolve from
the user's module cache, and `go` silently becomes the system **go1.19.8**.

The simd variants failed loudly there, which is the only reason this surfaced. A
variant that does not import simd would have been built by a seven-year-older
compiler without a word. `bench` no longer depends on `build`, and measurement
01's `go tool objdump` regime check moved to build time — it writes
`bin/regime.txt`, which the measured pass reads into the result's `sources`.

## 13:40

Measurement 04's headline reversed under its own data. The recorded table says
`channel-batched` beats `direct` by about 2x at every sweep point. The `cores`
column says `direct` uses 1.0 and every other row uses 1.8-2.0. Multiplied out,
batched measures 0.95x-1.11x against direct across the whole sweep — level.

The structure converts a core into throughput and never makes the work cheaper,
and it charges 236x-466x in residence latency to do it. Both runs agree at all
eight points with matching checksums, so this is the finding rather than a
reading of one run.

## 14:30

Measurement 02's top half is unmeasurable and the instrument said so. Latency is
a `uint32` nanosecond field that clamps at 4.295 s; at 16 and 20 bursts/s the
scalar rows clamp 228,886 and 268,836 of 600,000 requests, and their recorded
spread of 0.0 is the ceiling rather than precision. Each row prints its own
`clamped=` count, so the finding excludes those points.

Within the unsaturated range the finding is a capacity knee, not an ordering
flip: between 4 and 8 bursts/s the scalar receiver's p50 goes 3.56 ms to 326 ms
while the simd receiver goes 588 µs to 635 µs. The prediction expected simd's
advantage to decay under contention because all three rows would queue behind an
identical burst. They do not reach the knee together, so the advantage grows to
514x instead.

## 15:10

Project 01 answered, partly. The ladder spans 8.67x worst-to-best, not the two
orders of magnitude the choice is usually argued with. 2.42x of it comes back
from keep-alives in Go's stdlib HTTP — the largest single lever in the table,
larger than any step of the ladder. Language beats wire, 2.64x against 1.87x,
which is what the `go-http` control was built to separate.

Unanswered: how many multiples separate Python over HTTP from `rsx-cast`, because
`rsx-cast` was never measured. Said so in `FINDING.md` rather than substituting
plain UDP for it silently.

## 16:05

Replication changed two claims, which is why the rule exists. Measurement 03 ran
a second time with the pinned cores 85.9% busy against 26.4% for the first, and
two of ten orderings moved. The gRPC row's fall to last place at 32 KiB does not
replicate — it lands within 6% of `py-http` and the runs disagree — so the
finding states the collapse and withdraws the final position. The headline went
from the single cell 8.67x to the range 7-9x.

The other moved ordering was the opposite of a problem. `py-ws` worst against
`py-http` worst reads 1.01 and 0.99 at 8 KiB: the rows order oppositely there
because that is the crossover, located to one sweep point by two runs, which
confirms the prediction's "about 8 KiB".

Measurement 02 replicated at 81.7% busy against 24.5%. The knee holds, the two
light contention levels reproduce to within 0.1x and the cores column to within
0.04. Past the knee the ratio reads 514x and 392x, so it is quoted as two orders
of magnitude rather than as a figure.

## 16:20

`bench.record` named result files by date alone, so the 03 replication was about
to overwrite the run it was meant to be compared against. Caught it before the
write, preserved the first file, and fixed the cause: the name now carries the
minute. I briefly renamed the preserved file with a timestamp I invented rather
than read; corrected to its real write time, and renamed every existing result to
the same convention.

## 16:40

Wrote `notes/attack.md`, the project-level case that the whole thing is
worthless, which the method requires before publishing and which this project did
not have. Four attacks survived and changed the text: it measures an echo and not
a service call, so the crossing figures are a floor; contention inflates the slow
rows more than the fast ones, so the spread is a ceiling; the headline rested on
one cell; and 04's per-core figure is derived rather than recorded.

Published to `/srv/data/arizuko_krons/web/pub/service-boundary-cost/`, a
self-contained page in the house style, leading with the floor and ceiling
caveats rather than burying them.
