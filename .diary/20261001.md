## 05:24

The first run under the new harness recorded the pinned cores as 99.5% busy on
a box measured at 25-38% busy moments earlier. `claim()` built and then sampled,
so the reading caught its own compile. It now samples before it builds anything,
hands the value across the `sudo` boundary in `dist/prerun.json`, and returns it.
`bench.before()` is gone: the reading is taken at the one correct moment and read
back rather than re-sampled.

## 07:00

The status gate was judging the wrong thing, and `BUGS.md` had carried the
proposal since 2026-09-27. The load average counts runnable and uninterruptible
tasks rather than CPU time, so a variant that spawns threads inflates it by its
own thread count: measurement 02's sleeper variant drove it to 81.6 on a two-CPU
box with eleven tasks runnable and none blocked on I/O. A gate on that number
grades the workload, so 02 could never pass one that 04 could. The fifteen-minute
decay tail does the rest, which is why four runs in a row downgrade each other.

The status now decides on `busy_on_pinned_cores_at_start` against
`QUIET_CORES`, at the 10% the proposal named. The load average stays as
`host_load_at_start` and decides nothing. This is a method change: results
written before it are labelled by the old gate and are not comparable with ones
written after, and the superseded files stay as they are.

The commit that shipped it, `b0589c1`, justified it with a mechanism that is
wrong — it claimed the load average counts tasks across sixteen host CPUs while
the measurement runs in a two-CPU cpuset. This box has two CPUs, full stop.
`BUGS.md` records both the change and the bad reason, so the correction can be
audited instead of quietly replaced.

## 07:05

Measurement 01 refused every escalated run with "GOEXPERIMENT=simd is required;
run make bench" while `make bench` was exactly what had been run. `sudo` resets
the environment, so the measured pass no longer sees what `measurement.mk`
exports. The requirement is about compiling the simd variants and only the
unprivileged pass compiles, so the check moved into `build()`.

## 07:32

All four measurements have fresh runs, and all four are `status: structure`. The
pinned cores read 99.0%, 99.5%, 100.0% and 100.0% busy at the start. No run has
ever started with them under 25% busy, so this box cannot certify a baseline at
all. That is the honest label, not a failure of the runs, and loosening the
threshold until it passed would have been the one mistake the harness exists to
prevent.

The transport ladder replicated for a third time and that is the day's real
result. With the pinned cores 26.4%, 85.9% and 99.5% busy, the 128 B spread read
8.67x, 8.97x and 8.82x, and both ends held their identity: `py-http` untuned
slowest at 316.6, 316.8 and 311.1 µs, `go-udp` tuned fastest at 36.5, 35.3 and
35.3. A 3.8x change in neighbour load moves the headline 3.5%, which makes it
the most replicated number in the project. Measurement 04 replicated too: same
ordering at every sweep point, medians within about 20%, tighter spreads, and
checksums matching the earlier runs.

## 07:50

Investigated what it would take to get a quiet box. The neighbours are five
docker containers on cores 0 and 1 — one `node` at 15.9%, two `extenddb` at 4.8
and 4.3, two `routd` at 4.2 and 3.6 — about a third of one core between them, so
stopping them would take the floor near zero and clear the 10% gate. They are
systemd units, so the cycle is reversible and `arizuko_krons` already does a full
compose `down` in its own `ExecStartPre`.

Not done. `arizuko_krons` alone runs eleven containers including `proxyd`, which
serves the pages this project publishes, plus the Telegram and WhatsApp bots and
TTS. Those are live services and the blast radius is the operator's call, so the
plan is written down and waiting rather than executed.

Both published pages were refreshed to lead with the fact that nothing here is
`verified`, and both return 200.
